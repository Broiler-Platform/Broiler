# Pending submodule patches

Fixes that belong in a submodule (`Broiler.HTML`, `Broiler.CSS`, `Broiler.DOM`,
`Broiler.JS`, `Broiler.Graphics`) but could not be pushed to their remote from
the session that wrote them: the git proxy only authorises repos in the session's
GitHub scope, so a push to a submodule remote outside it returns **403**. Rather
than bump a submodule pointer at a commit CI cannot clone, the change is captured
here as a `git format-patch` file for a maintainer to apply.

The directory is a backlog, not an archive: it holds only what is *currently*
pending. A patch is deleted from here, along with its row below, once its fix is
upstream and the submodule pointer is bumped.

## Applying

```sh
cd <Submodule>
git am --keep-cr ../patches/NNNN-<slug>.patch
git push origin HEAD
cd ..
git add <Submodule>        # bump the pointer only after the push succeeds
```

**`--keep-cr` is not optional for a patch that touches a file with CRLF line endings**, which
several `Broiler.JS` sources are (mixed CRLF and LF, within one file). `git am` runs the patch
through `mailinfo`, which normalizes the line endings of the diff body unless told not to — so the
context lines stop matching the file and the apply fails with *"patch does not apply"* on a patch
that is perfectly good. `git apply` does not have the problem, which is exactly why it is not the
check: these instructions use `am`, so `am` is what a patch has to survive. Verified per patch by
applying it to a clean checkout of the pinned pointer and diffing the result against the branch it
was generated from.

## Exercised on CI before they land

`scripts/apply-pending-wpt-patches.sh` applies the patches listed in its
`PENDING_PATCHES` array to the checked-out submodule trees before the WPT run, so
a pending fix is reflected in CI's numbers rather than waiting on the pointer. It
is idempotent — a patch already contained in the pinned pointer reverse-applies
and is skipped — so an entry stops applying by itself once a maintainer lands it.

| `0131-html-relayout-invalidation-ledger` | `Broiler.HTML` | **`HtmlContainerInt` asks what changed before it rebuilds the render tree, instead of only whether something did.** Multithreading roadmap item #14, first slice — 30 lines, because the type it calls (`Broiler.Layout.Engine.RenderTreeInvalidation`) is in the main repository. **What it replaces:** `EnsureBoundDocumentCurrent` compared a bound `DomDocument`'s `Version` against a copy and, on any difference, called `BuildBoundDocument` — which disposes the render tree and regenerates box tree and full cascade before the layout pass runs. The relayout profile measured that rebuild at **60–97% of a relayout** (97.1% on the rule-heavy corpus page), so the version counter was the most expensive boolean in the engine: it says "something changed" and nothing else. **The blocker the roadmap named did not exist.** Item #14 was recorded as starting in `Broiler.DOM`, "giving mutations a shape a consumer can act on". `DomDocument.Mutated` has published a typed `DomMutationRecord` — type, target, added and removed nodes, attribute name, old and new value — for as long as `MutationObserver` has worked. What was missing was a consumer, and it is on this side. **What it elides, and why that is provable rather than heuristic:** one rule — a record whose target does not hang off the bound document cannot have changed anything the render tree shows, because the box tree is built by walking that document and nothing else. `ChildList` records name the *parent*, which is what makes the test sound in both directions: nodes added to a detached parent are themselves detached, and a node moved *out* of the page is reported against the still-connected parent it left. **What it deliberately does not elide:** anything connected, including a `data-*` write no selector can reach — that needs the cascade to answer whether a rule's subject could match differently, which is the rest of the item. **The backstop is what makes it safe against the case it cannot see:** the ledger records the version each record arrived at, and answers "rebuild" unconditionally if the counter has moved further than the records account for (an unobserved publish path, an earlier subscriber that threw, a document mutated before it was bound). An elision is only possible when every bump since the last build is accounted for. **Measured, paired against the pinned pointer on one host** (`--relayout-profile`, 4 cores, medians of 5): the offscreen-build row goes from a full rebuild to none on all five corpus pages — `rules` **1 032.7 → 11.5 ms (89.8×)**, `boxes` 264.2 → 10.3 (25.8×), `paint` 224.8 → 9.9 (22.6×), `mixed` 116.9 → 7.2 (16.3×), `text` 117.2 → 11.7 (10.0×). `0128` (`Broiler.CSS`, cache sharding), `0129` (`Broiler.HTML`, cascade sub-stage
trace and warm pass) and `0130` (`Broiler.JS`, test parallelization) were the
previous entries. All three are upstream and all three submodule pointers are

of this file: the directory is a backlog, not an archive.

**How to tell, rather than assume.** A patch is upstream when it *reverse-applies*
to the pinned pointer's tree — `cd <Submodule> && git apply --reverse --check
../patches/NNNN-<slug>.patch` succeeding means the fix is already there. That is
the same test `apply-pending-wpt-patches.sh` uses for its idempotence guard, and
it is worth running over the whole directory at the start of a task: a patch that
has landed since the file was last edited is otherwise indistinguishable from one
that has not, and re-applying it fails confusingly rather than harmlessly.

**One way that check lies, and it lied here.** A reverse-check also fails when the
paths in the patch do not resolve, which looks exactly like "not upstream" and is
not the same claim. `0130` was generated from a tree whose paths carried an extra
leading directory, so the check needs `-p2`; at the default strip level it reports
*"No such file or directory"* and the fix was upstream all along. Read the failure
before believing it, and settle it by reading the target file — which is what
established all three of the retirements above.
